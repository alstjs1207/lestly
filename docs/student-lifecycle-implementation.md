# 졸업과 탈퇴 정책 구현 및 로컬 검증

2026-10-25 · 원본 저장소: `/Users/msyu/study/lestly`

## 구현 내용

- 졸업·탈퇴 시 시작 전 예약을 자동 취소하고, 미사용 초대와 대기 중 수업 알림을 중단한다. 진행 중 수업은 종료 후 처리하며 완료 기록은 유지한다.
- 확인 화면에 취소 건수를 표시한다. 확인 후 예약이나 대상 상태가 바뀌면 다시 확인받으며, 취소 실패 시 상태와 수강 기간 변경도 롤백한다.
- 수강 종료일을 앞당기면 새 종료일 다음 날 한국 시각 00:00 이후 시작하는 예정 예약을 취소한다. 단건·반복 모두 적용한다.
- 관리자 단건·반복 예약 등록과 변경에 수강 기간 검사를 적용한다. 반복 예약의 생성·변경은 한 트랜잭션이며 일부 회차만 저장되지 않는다.
- 졸업생은 로그인과 본인 완료 수업·수업명·강사 조회를 허용하고 예약·초대는 차단한다. 탈퇴자는 로그인과 데이터 접근을 차단하며 기존 Auth 세션과 JWT의 접근도 무효화한다.
- 재원 복귀 시 다시 로그인할 수 있고 기존 학습 기록을 유지한다. 취소한 예약·알림·초대는 되살리지 않는다. 별도 수강 회차나 상태 변경 이력 기능은 추가하지 않았다.

## 성능 확인

로그인 차단 여부와 필요한 프로필을 하나의 RPC로 받아 요청 내에서 재사용한다. 학습 홈과 레이아웃의 학원 조회도 공유한다. 일정 조회마다 취소 건수를 조회하거나 브라우저에서 상태를 주기적으로 확인하는 요청은 추가하지 않았다.

권한 검사는 행마다 반복하던 관리자·소속 확인을 SQL InitPlan으로 바꿔 조회당 한 번 계산한다. 취소 대상에는 `(organization_id, student_id, start_time)` 인덱스, 예약 알림에는 `schedule_id` 인덱스를 사용한다. 반복 예약 변경은 회차별 HTTP 요청 대신 한 번의 RPC로 처리한다.

PGlite에 동일한 수업 10,001건을 넣고 0024 이전 권한 정책과 변경 정책을 비교했다. 워밍업 1회 후 5회 실행의 중앙값이다.

| SQL 작업 | 이전 | 변경 후 |
| --- | --- | --- |
| 학생 최근 수업 50건 | 0.821ms | 0.596ms |
| 관리자 일정 존재 확인 | 0.146ms | 0.544ms |
| 학생 완료 시간 합계 | 113.882ms | 5.041ms |

예정 예약 1,000건의 졸업 처리와 일괄 취소도 한 트랜잭션으로 검증했으며 로컬 실행은 약 107.9ms였다. 네트워크, Supabase와 Vercel 실행 환경을 제외한 수치이므로 실제 화면 응답 시간이나 운영 처리량을 보장하는 값은 아니다.

재현: `npm run test:db`. 측정 원자료는 실행 시 `test-results/student-lifecycle-performance.json`에 생성된다.

## 검증과 한계

- Node.js 24.22.1에서 단위 테스트 141개, 실제 마이그레이션 재생을 포함한 DB 검사 64개, 타입 검사와 프로덕션 빌드를 수행했다.
- DB 검사는 계정·학원 격리, 졸업생 읽기 권한, 탈퇴 후 JWT 차단, 재등록, 종료일 경계, 취소 대상 변경, 롤백, 반복 예약 전체 롤백과 초대·알림 재발송 방지를 포함한다.
- 로그인 완료 경로의 차단, 변경 확인 응답, 요청 내 인증·프로필 조회 공유는 실제 핸들러와 클라이언트 모의 객체로 검증한다.
- 기존 Supabase에서 관리자·재원생·졸업생 권한을 읽기 전용으로 확인했고, 졸업생은 완료된 본인 수업 7건을 읽을 수 있으며 미래 수업은 조회되지 않았다. 실제 두 DB 연결에서 임의 키의 트랜잭션 잠금 대기·해제도 확인했다. 실제 학생 예약을 동시에 변경하는 부하 시험과 외부 메시지 발송은 하지 않았다.

JWT 만료까지 기다리지 않고 접근을 차단해야 한다는 인증 기준은 [Supabase 세션 문서](https://supabase.com/docs/guides/auth/sessions)를 참고했다. 재등록 후에도 이전 JWT를 재사용하지 못하도록 세션 무효화 기준을 유지한다.

## 적용 상태

새 DB 생성은 하지 않았다. 이후 사용자가 기존 공용 DB 변경과 preview 앱 배포를 승인했다. 0024를 기존 프로젝트에 적용했고, 프로필 36건·소속 35건·수업 1,452건과 기존 예약·알림·초대 데이터의 전후 해시가 동일함을 확인했다. 적용 기록은 `sql/operations/20261025_student_lifecycle_apply.result.json`에 보존한다. 앱은 preview 브랜치에만 배포하며 main 앱 배포는 진행하지 않는다. 작업은 원본 저장소에서 수행했고 별도 worktree나 clone은 만들지 않았다.

기존 preview와 main은 DB를 공유하므로 DB의 예약·권한 규칙은 양쪽에 적용된다. 앱은 preview에서 확인한 뒤 별도로 운영 배포한다. DB의 발송 상태 전환 검사는 적용됐다. `send-alimtalk`의 추가 RPC 재검사는 도입 효과가 작아 사용자 요청으로 코드에서 제거했다. 해당 패치는 공용 함수에 배포되지 않았으며, 공용 함수의 배포된 코드는 유지한다.

수강 기간이 공용 프로필에 있는 현재 구조에서, 다른 학원의 데이터를 건드리지 않도록 타 학원 소속이 있는 학생의 기간 변경은 권한을 확인하고 차단한다. 복수 학원 전환 기능은 이번 작업에 추가하지 않았다.

## 일반 수정과 상태 변경 확인 흐름 단순화

- `0025_student_edit_fast_path`에서 이름·연락처 등 일반 수정은 예약 잠금과 취소 영향 조회를 생략한다. 상태·유형·수강 기간은 이 경로에서 쓰지 않으므로, 동시에 처리한 졸업이나 수강 기간 변경을 덮어쓰지 않는다. 실제 상태·기간 변경에는 기존 예약 잠금을 유지하고, 졸업·탈퇴 또는 종료일 단축 시에만 취소 확인을 수행한다.
- 졸업·탈퇴 창을 열 때 현재 종료일을 기준으로 취소 건수와 확인 토큰을 조회한다. 정상 흐름은 최종 확인 한 번으로 처리한다. 예약 변경 시 재확인, 진행 중 수업 차단, 조회 실패 시 제출 차단, 닫았다 다시 열 때 새 조회, 처리 중 중복 클릭 방지를 유지한다.
- Node.js 24에서 단위 테스트 143개, DB 검사 68개, 타입 검사와 프로덕션 빌드가 통과했다. 로컬 브라우저에서 실제 컴포넌트를 모의 서버 응답에 연결해 정상 제출·재확인·조회 실패와 재시도·재열기·진행 중 수업·중복 클릭을 확인했다. 실제 학생 상태나 예약을 변경하는 화면 테스트는 하지 않았다.
- 동일한 학생의 일반 수정 SQL을 PGlite에서 워밍업 후 7회 측정한 중앙값은 이전 0.508ms, 변경 후 0.169ms였다. 측정 원자료는 `test-results/student-edit-performance.json`에 생성된다. 네트워크를 제외한 로컬 비교이며 실제 서비스 응답 시간을 보장하지 않는다.
- 기존 공용 DB에 0025를 적용했다. 프로필·소속·예약·알림·초대의 전후 해시와 저장 함수의 권한이 동일했다. 적용 기록은 `sql/operations/20261025_student_edit_apply.result.json`에 보존한다. 신규 DB나 별도 작업용 저장소는 만들지 않았다.

# Lestly 보안 성능 리팩토링 검토

2026년 10월 3일 기준으로 React Router 애플리케이션, 인증·관리자 API, 공개 상담, 알림·결제, Supabase Edge Function, SQL 마이그레이션과 권한 정책을 검토했다. 확인된 문제는 로컬 코드에 수정했고 회귀 검증을 추가했다. 운영 환경의 보안 조치는 새 애플리케이션과 Edge Function 배포, 데이터베이스 마이그레이션 적용 후 활성화된다.

운영 DB, 사용자 계정, 문자·메일·결제 시스템에는 쓰기 요청을 보내지 않았다. 이 문서는 수정 결과와 배포 전 검증 사항을 구분한다.

React Router를 7.5.1에서 7.18.4로, Vite를 5.4.18에서 5.4.21로 올렸다. React Router의 Framework Mode manifest DoS는 7.18.0부터 수정된 것으로 [공식 보안 공지](https://github.com/remix-run/react-router/security/advisories/GHSA-chx6-hx7r-mcp5)에 명시되어 있다. Vite host 설정 변경은 [공식 문서의 DNS rebinding 경고](https://vite.dev/config/server-options#server-allowedhosts)에 따른 조치다. 전체 의존성 취약점 검사가 완료되었다는 의미는 아니다.

## 성능과 유지보수 개선

- 관리자 학생 통계를 전체 행 다운로드 후 계산하던 방식에서 count-only 조회로 변경했다. 1,000건을 넘는 데이터도 정확히 센다.
- 누적 수강시간을 RLS를 유지하는 SQL 집계 RPC로 변경했다. 마이그레이션 전에는 같은 권한·조직 범위를 유지하는 페이지 조회로 대체한다.
- 일정·충돌 검증·연간 통계의 API 행 제한으로 인한 누락을 보완하고 KST 월 경계를 다음 달 시작의 미포함 범위로 통일했다.
- 학생 상세 조회를 2회에서 1회, 월별 통계를 2회에서 1회로 줄였다. 전체 조직 통계는 조직당 3회 추가 요청 대신 페이지당 한 번 조회한다.
- 검색값을 PostgREST OR 문법에서 인용하고 페이지 크기·월 범위를 검증했다. 관리자 학생 일정에 조직 필터를 적용했다.
- 잘못된 관계 이름으로 비어 있던 슈퍼관리자 캘린더를 수정했다. 신규 복합 FK와 기존 FK가 공존해도 모호하지 않도록 기존 관계 이름을 명시했다. [PostgREST 관계 힌트 문서](https://docs.postgrest.org/en/stable/references/api/resource_embedding.html#foreign-key-joins-on-multiple-foreign-key-relationships)를 참고했다.
- 연속 학습일 계산은 첫 누락일까지 조회하며 같은 KST 날짜의 중복 기록을 처리한다. 캘린더의 월 URL 직접 접근과 인증 갱신 헤더 전달도 수정했다.
- 법률 문서는 허용된 두 slug만 읽고 운영 환경에서 컴파일 결과를 재사용한다. SSR 초기화 실패·종료·취소 시 promise와 timer가 정리된다.

실사용 지연 시간이나 운영 부하를 측정하지 않았으므로 개선율을 백분율로 주장하지 않는다. 요청 수 감소와 대량 데이터 정확성은 테스트로 확인했다.

## 로컬 검증

- `npm run test:unit`: 70개 통과. 인증·입력·실제 route handler·Edge 권한·Resend HTTP 요청·React SSR·대량 조회 회귀 테스트.
- `npm run test:db`: 전체 17개 마이그레이션 재생, SQL·RLS 검증 13개 통과. 자세한 범위는 [SQL 검증 안내](../sql/checks/README.md).
- `npm run typecheck`와 프로덕션 빌드 통과.
- 더미 설정으로 운영 모드 로컬 HTTP 검사 11개 통과: 로그인 렌더링, debug·결제 데모 404, 외부 Origin 거부, 상담 크기·JSON 오류, 변경 메서드·크론 인증 거부.
- npm lockfile의 offline dry-run 일관성 검사 통과.
- 생성된 client build에서 비공개 환경값과 공개 `.map` 파일이 발견되지 않음. 이는 검사한 환경값과 해당 로컬 빌드에 한정된다.

외부 계정 생성·삭제와 실제 발송이 포함된 기존 E2E는 실행하지 않았다. pg_cron·pg_net, Realtime, 실제 동시 트랜잭션과 PostgREST schema cache는 staging 검증이 필요하다.

## 운영 반영 순서

1. 실제 Supabase와 같은 설정의 staging에서 새 앱과 명시적 FK 관계 힌트를 검증한다. 앱은 SQL RPC가 없어도 대체 조회를 사용하므로 앱 변경을 먼저 반영할 수 있다.
2. 새 `send-alimtalk` 함수와 공통 인증 모듈을 함께 배포하고 service-role 호출 성공·anon 및 일반 사용자 호출 거부를 확인한다.
3. `0016_tenant_security_and_schedule_stats.sql`을 적용한다. 기존 데이터는 바꾸지 않으며 `NOT VALID` 제약은 새 쓰기에 적용된다.
4. [테넌트 사전 검사 SQL](../sql/checks/tenant_integrity.sql)을 읽기 전용으로 실행한다. 발견한 기존 데이터 오류를 검토·정리한 뒤 제약을 VALIDATE하고 PostgREST 관계 캐시를 확인한다.
5. 관리자 생성·초대 수락·학생 예약·공개 상담·알림의 정상 흐름과 권한 거부 흐름을 staging에서 검증한다.

`DEV_ALLOWED_HOSTS`는 개발 환경의 추가 host가 필요할 때만 쉼표로 구분해 설정한다. 결제 예제는 운영에서 404를 반환한다. 실제 유료 서비스 결제에는 별도의 서버 주문 저장·주문 소유권·멱등 처리 설계가 필요하다.

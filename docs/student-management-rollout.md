# 수강생 관리 변경 적용

이 변경은 `0018_student_management_integrity.sql`을 먼저 적용한 뒤 앱을 배포한다. 기존 DB에 앱 코드만 배포하면 정규화 전화번호 조회와 `save_managed_student` RPC가 존재하지 않아 등록·수정·전화번호 검색이 실패한다.

1. `sql/operations/20261022_student_phone_conflicts.sql`을 실행해 학원별 중복 전화번호를 확인한다. 졸업·탈퇴 학생도 포함한다.
2. 중복이 있다면 운영자가 실제 학생 정보를 확인하고 올바른 전화번호로 정정한다. 이 마이그레이션은 학생을 자동 병합하거나 삭제하지 않으며, 중복이 남아 있으면 중단된다.
3. 기존 마이그레이션 절차로 0018을 적용한 뒤 앱을 배포한다. 생성 타입과 Drizzle 스키마도 이번 변경에 포함되어 있다.

운영 DB의 Drizzle 이력이 0015에서 멈추고 0016이 보류 중인 경우, 전체 `db:migrate`로 보류 항목까지 적용하지 않는다. 0017과 동일하게 0018 SQL만 하나의 트랜잭션으로 적용하고, Drizzle 이력을 0018로 건너뛰지 않는다. 0018은 재실행할 수 있도록 작성되어 있어 이후 정규 배포에서 0016·0017·0018을 순서대로 다시 적용할 수 있다. 적용 시 SQL 해시와 검증 결과를 별도 작업 기록으로 보존한다.

전화번호 원본 표시는 유지하고, `profiles.phone_normalized`와 학원별 고유 키를 사용해 검색 및 중복을 처리한다. 수강생 등록·수정은 인증된 관리자의 RPC 트랜잭션으로 저장한다. 기존 회원 연결, 초대 및 N:N 소속은 유지된다.

일괄 입력 명단은 같은 탭의 sessionStorage에 사용자·학원별로 최대 24시간 보존한다. 복원 시 자동 등록하지 않으며, 저장 완료된 행은 재등록에서 제외한다. ‘명단 초기화’로 임시 저장을 지울 수 있다.

검증: `npm run test:unit`, `npm run test:db`, `npm run build`. DB 검사는 격리된 PGlite에서 마이그레이션 전체 적용, 권한, 고유 제약, 저장 실패 시 롤백을 확인한다. 실제 Supabase의 여러 연결을 사용한 동시 요청은 별도 배포 환경에서 확인한다.

2026-10-22 운영 DB에는 위 절차대로 0018만 별도 적용했다. 사용자 승인을 받아 기존 테스트 번호 2건을 서로 겹치지 않게 정정했으며, 프로필·소속·수업 이력과 기존 초대 RPC 보존 및 PostgREST 스키마 인식을 확인했다. 상세 검증 결과는 `sql/operations/20261022_student_management.result.json`에 기록했다. 0016 보류 상태와 Drizzle 이력은 유지되어 있다.

# 소규모 수업 운영 공통화 계획

2026-10-28. 기존 예약·수강생·출결·학습 기록을 유지하며 단계별로 진행한다.
각 Phase가 끝나면 멈추고, 사용자의 다음 단계 요청 후 진행한다.

## 단계

| Phase | 범위                                                                    | 상태                |
| ----- | ----------------------------------------------------------------------- | ------------------- |
| 1     | 지역 선택 입력, 유형 문자열 전환, 학생·성인 기본 분류, 기존 데이터 보존 | 실제 DB 적용 완료, 프리뷰 배포 검증 중 |
| 2     | 조직별 유형 추가·이름 변경·비활성화·순서·기본값 관리                    | 실제 DB 적용 완료, 프리뷰 배포 검증 중 |
| 3     | 수업 길이·시작 시각 범위·간격·접수 마감 공통화 및 정원 계산 보완        | 대기                |
| 4     | 월별 오픈·오늘 기준 N일 예약 기간                                       | 대기                |
| 5     | 기존 예약 조건을 보존하는 학생 취소 정책                                | 대기                |

## Phase 1

- 지역은 모든 조직에서 선택 입력이며, 미입력·빈 문자열·공백은 NULL로 저장한다.
  기존 지역은 마이그레이션에서 바꾸지 않는다. 수정 화면에서 지역을 지우고 저장하면 NULL이 된다.
- 수강생 유형 `organization_members.type`은 PostgreSQL enum에서 text로 전환한다.
  표시명은 학생·성인, 내부 코드는 STUDENT·ADULT다. 계정 역할(role)과는 별개다.
- EXAMINEE와 DROPPER는 STUDENT로 통합하고 ADULT는 유지한다.
  DROPPER였던 수강생은 기존 설명을 보존하며 `[이전 유형: 재수생]`을 한 번 추가한다.
  원래 분류가 없던 소속은 임의로 분류하지 않으며, 관리자 소속의 NULL도 유지한다.
- 유형은 등록·수정 시 필수다. 기본값은 STUDENT다.
  조직별 `organization_student_types`에 기본 두 유형을 저장하고 복합 외래 키로
  타 조직 전용 유형·존재하지 않는 유형을 막는다. 새 조직에도 기본 목록을 자동 생성한다.
  이 단계의 인증된 사용자는 목록을 읽을 수만 있고, 유형 편집 UI/API는 Phase 2에서 만든다.
- 화면의 등록·수정·상세·목록 필터·일괄 등록은 같은 기본 분류 정의를 쓴다.
  과거 일괄 등록 초안과 붙여넣기의 입시생·재수생 값은 학생으로 변환하고 재수 이력은 설명에 전달한다.
- DB 저장 RPC는 구버전 호출의 EXAMINEE·DROPPER도 받아 STUDENT로 정규화한다.
  구버전 화면의 선택지까지 자동으로 호환되는 것은 아니므로 DB와 새 앱의 적용은 함께 계획한다.
- 예약·출결·수강 기간·졸업·탈퇴·초대·연락처 중복 정책은 유지한다.

### 파일과 적용

- 마이그레이션: `sql/migrations/0029_student_metadata.sql`
- 검증: `npm run test:unit`, `npm run test:db`, `npm run typecheck`, `npm run build`
- DB 검사는 격리된 PGlite에서 전체 이력 및 기존 데이터 전환을 검증한다.
- Node 24.22.1에서 단위 테스트 167개, DB 회귀 검사 84개와 기존 데이터 전환 검사를 통과했다.
  타입 검사와 프로덕션 빌드도 통과했다. 빌드 산출물은 생성됐으나 로컬 Sentry 소스맵 업로드는
  기존 환경의 `unable to open database file` 경고가 발생했다.
  빌드된 출결·학생 일정 라우트의 SSR 검사도 통과했다.
- 로컬 구현 단계에서는 실제 DB 적용·배포를 수행하지 않았다. 아래 실제 적용 기록을 따른다.
  배포 시 백업과 실제 스키마·기존 분류 건수를 확인하고, 0029 적용 후 새 앱을 배포한다.
  이 전환을 되돌릴 때는 유형만 역변환하면 입시생·재수생을 구분할 수 없으므로 적용 전 데이터를 사용한다.
- 작업 경로는 원본 `/Users/msyu/study/lestly`다. 별도 worktree·clone은 만들지 않았다.

## Phase 2

- 현재 분류 테이블을 확장해 표시명·순서·활성 여부·기본값을 관리한다.
- 활성 유형은 조직마다 최소 1개, 기본값은 그중 1개를 보장한다. UI와 DB 모두 검증한다.
- 사용 중인 유형은 비활성화해 신규 선택에서 제외하고 기존 학생의 값은 유지한다.
  기존 비활성 유형을 변경하지 않는 일반 정보 수정도 허용한다.
- 조직별로 조회한 목록을 등록·수정·일괄 등록·필터에 연결한다.
- 과정(취미반·자격증반) 및 수업 방식(개인·그룹)은 학생 유형에 섞지 않는다.

### Phase 2 구현과 검증

- `/admin/settings`의 **수강생 유형**에서 이름·사용 여부·순서·기본값을 함께 저장한다.
  유형은 최대 50개이며, 저장된 유형은 삭제하지 않고 비활성화한다. 내부 코드는 변경하지 않는다.
- 기본 유형을 중지하려면 먼저 다른 활성 유형을 기본값으로 선택한다.
  사용 중인 유형이 없는 상태나 기본값이 없거나 여러 개인 상태는 UI/API/DB에서 거절한다.
- 개별 등록·수정·일괄 등록·붙여넣기·상세·목록 필터는 인증된 조직의 목록을 조회한다.
  필터와 상세에는 비활성 유형의 이름도 남는다. 기존 비활성 유형을 유지하는 수정은 허용한다.
- `save_student_types`가 조직 행을 잠근 뒤 목록 전체를 원자적으로 저장한다.
  처음 불러온 목록과 실제 목록이 달라지면 409 충돌을 반환하며 입력 내용은 유지한다.
  ‘최신 목록 불러오기’는 미저장 변경을 버릴지 확인한 후 다시 조회한다.
- DB의 지연 제약 트리거가 활성 유형·기본값·이름·순서의 유효성을 검사한다.
  직접 분류 테이블 쓰기는 인증 클라이언트에 허용하지 않는다. 소속 변경 트리거는 신규 비활성 유형 지정을 막고
  기존 유형을 그대로 유지하는 변경은 허용한다. 기존 NULL 분류는 유지하며 학생 저장 API는 유형을 필수로 받는다.
- 추가 마이그레이션: `sql/migrations/0030_organization_student_types.sql`.
  실제 적용은 0029 → 0030 → 새 앱 배포 순서를 사용한다. 로컬 구현 이후의 실제 적용 기록은 아래를 따른다.
- `npm run test:student-types:ssr`는 빌드된 설정·일괄 등록·목록·상세 화면을 샘플 loader 데이터로 검증한다.
  UI 검증도 실제 DB에 연결하지 않는 샘플 컴포넌트 화면에서 수행한다.
- 검증 결과: Node 24.22.1, 단위 테스트 172개, DB 회귀 검사 89개 및 0029·0030 기존 데이터 전환 검사 통과.
  타입 검사·프로덕션 빌드와 유형 설정/일괄 등록/목록/상세 SSR, 기존 학생 일정·출결 SSR도 통과했다.
- ego-browser에서 실제 컴포넌트를 샘플 데이터로 렌더링하여 유형 추가·순서·기본값·비활성화·저장,
  신규 등록의 활성 목록, 기존 비활성 유형 유지, 편집 충돌→최신 목록 재조회→재저장을 확인했다.
  데스크톱 1440px·모바일 375px에서 가로 넘침이 없음을 확인했다.

## Phase 3

- 수업 길이는 분 단위 복수 목록과 기본값으로 설정한다. 기본값은 목록 안에 있어야 한다.
  기존 조직의 실제 동작인 180·360·540분, 기본 180분을 유지한다.
- 시작 가능한 첫·마지막 시각과 간격을 설정한다. 기존 기본은 09:00~20:00·30분이다.
  마지막 시작 시각을 수업 종료 제한으로 해석하지 않으며 기존 자정 넘김 수업을 보존한다.
- 예약은 시작 N분 전까지 접수하도록 설정한다. 기존 기본은 추가 접수 제한 없음이다.
- 기존 요일·개별 시작 시각 차단은 신규 학생 예약에 적용하고 기존 일정은 보존한다.
- 정원은 조직 전체 기준을 유지한다. 단순히 겹치는 모든 예약을 합산하지 않고
  실제 최대 동시 인원을 계산한다. 예약 조회·저장·관리자 반복 일정·출결 복구가 같은 판정을 쓴다.
- 관리자의 학생 신청 제한 예외와 정원·학생 중복·소속·수강 기간 검증은 유지한다.
- 기존 선택지에서 제거된 길이를 표시·편집할 때 임의의 길이로 바꾸지 않는다.
- 설정 화면뿐 아니라 PC/모바일 예약, 관리자 폼, 캘린더, API, RPC·트리거를 함께 수정한다.

## Phase 4

- 월별: 지정일 한국 시간 00시부터 다음 달 신청을 허용한다. 없는 날짜는 말일에 연다.
  기존 조직은 매월 25일을 유지한다.
- 이동식: 오늘부터 N일 뒤 날짜까지 신청 가능하다. 과거 시각은 신청할 수 없다.
- 학생 수강 기간과 접수 마감을 함께 검사한다. 범위 밖에 이미 등록된 일정은 조회할 수 있다.

## Phase 5

- 전날까지 / 시작 N시간 전까지의 취소 규칙을 설정한다. 두 규칙은 서로 다르다.
- 기존 예약은 전날까지 규칙을 유지하고, 새 예약에는 당시 취소 규칙을 저장한다.
  이후 조직 설정 변경으로 기존 예약의 취소 기한을 바꾸지 않는다.
- 화면과 API 및 DB DELETE 접근 정책에서 같은 규칙을 적용한다.
- 당일 신청 후 직접 취소가 불가능한 경우 확정 전에 안내한다.

## 공통 보존·검증 기준

설정 변경 자체로 기존 예약이나 반복 회차를 수정·삭제하지 않는다.
정원을 줄여 기존 예약이 초과 상태가 되어도 예약을 보존하고 추가 신청을 제한한다.
한국 시간, 월말·연말, 동시 신청의 정원 경합, 설정 변경 전후 보존,
반복 일정 및 출결 복구를 해당 단계에서 검증한다.

회차별 모집, 강사별 정원, 클래스별 정책, 여러 조직 동시 수강 개선,
특정 날짜 휴무·요일별 시간표, 보강·수강권·결제·정산은 별도 확장으로 남긴다.

# 관리자 홈 지연 조사 (2026-10-24)

- 사용자가 다른 메뉴에서 관리자 홈으로 돌아올 때 약 3초 지연을 보고했다.
- Vercel 운영 배포 `f058f6b`의 15:20:18 KST 요청에서 `/admin.data?_routes=root,features/admin/screens/dashboard` 함수 실행 시간이 **3.47초**였다. iPhone Safari에서 강사 편집 화면을 거쳐 온 요청이다.
- 이 요청은 프로필·멤버십 확인 후 통계 HEAD 요청 8개와 향후 일정 GET 요청을 수행했다. 푸시 세션 동기화는 별도 요청으로 실행된다.
- 운영 `pg_stat_statements`에서 조직의 전체 일정 개수를 세는 PostgREST 쿼리는 조회 시점까지 31회, 평균 **728.75ms**, 최대 **2122.90ms**였다. 누적 통계이므로 이 최대값이 위 요청에서 발생했다고 단정할 수 없다.

## 확인한 병목과 수정

`getDashboardStats`는 초기 설정 안내에 일정·프로그램이 하나라도 있는지 표시하기 위해 전체 일정과 활성 프로그램의 정확한 개수를 계산했다. 전체 일정 집계는 날짜 제한이 없어 과거 이력이 늘어날수록 RLS 평가 비용도 증가한다. 관찰한 PostgREST 쿼리는 응답 행 집계와 전체 개수 집계에 각각 일정 조회를 수행했다.

- 설정 안내의 두 집계를 조직 범위를 유지하는 `LIMIT 1` 존재 여부 조회로 변경했다.
- 홈에서 표시하지 않는 졸업·삭제 수강생 통계 요청 2개를 제거했다.
- 홈 통계 요청이 8개에서 6개로 감소했다. 카드에 표시하는 전체·정상 수강생 및 오늘·월간 일정의 정확한 개수는 유지한다.
- 기존 일반 Supabase 클라이언트와 RLS를 그대로 사용한다. 마이그레이션은 필요하지 않다.

## 읽기 전용 비교 측정

운영 DB에서 관리자별 JWT claim과 `authenticated` 역할을 트랜잭션 안에 설정해 RLS를 적용했다. PostgREST의 기존 전체 집계 구조와 변경한 존재 여부 SQL을 각각 세 번 실행했다. 모두 `READ ONLY` 트랜잭션이며 실제 데이터는 변경하지 않았다.

| 조직 일정 수 | 기존 전체 집계 실행 시간 | 변경한 존재 여부 조회 실행 시간 |
| ------------ | ------------------------ | ------------------------------- |
| 282건        | 66.1–82.6ms              | 0.55–0.58ms                     |
| 1,170건      | 302.0–314.6ms            | 0.57–0.62ms                     |

위 수치는 네트워크·인증·나머지 쿼리를 제외한 SQL 실행 시간이다. 운영 배포 후 관리자 홈 전체 응답 시간을 다시 비교해야 하며, 전체 홈이 0.6ms로 빨라진다는 의미는 아니다. 갑작스러운 지연 증가의 단일 계기까지는 확인하지 않았다.

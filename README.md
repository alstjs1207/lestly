# Lestly

소규모 클래스 및 샵 운영자를 위한 예약·상담·수강생 관리 SaaS
클래스 홍보, 상담 접수, 수강생 관리, 스케줄 운영을 하나의 서비스로 제공하는 플랫폼

공통화 단계별 계획: [소규모 수업 운영 공통화](docs/service-generalization-plan.md)

수강생 운영 정책안: [수강 종료와 탈퇴](docs/student-lifecycle-policy.md)

## 예약 처리 정합성 수정

반복 첫 회차 취소 후 남은 회차 관리, 다른 학생으로 옮긴 회차의 분리, 취소·변경 안내, 일부 등록 실패, 비활성 클래스 이동과 복수 조직 예약을 보완했다. 기존 예약과 출결·취소 정책은 보존한다. 적용 순서와 9개 수정·회귀 검증은 [예약 처리 정합성 수정](docs/booking-integrity-fixes.md)을 따른다.

## 설정 영역별 저장

설정 화면을 새 클래스 기본값·예약 기간·예약 시간·휴무 요일·취소 기한·수강생 유형으로 나누고 각 영역을 따로 저장한다. 다른 영역의 미저장 입력은 유지하며 저장 결과도 해당 영역에 표시한다. 서버는 최신 설정에 선택한 영역의 값만 합쳐 저장한다. 모바일에서는 상단 탭으로 선택한 영역만 표시하고, 탭을 바꿔도 입력과 저장 상태를 유지한다. 자세한 내용은 [설정 영역별 저장](docs/settings-sections.md)을 참고한다.

## 클래스별 예약 정책

수업 길이와 정원은 각 클래스의 실제 예약에 적용한다. 조직의 수업 길이·정원은 새 클래스를 만들 때 한 번 복사하는 기본값이다. 조직 기본값을 바꿔도 기존 클래스와 예약은 유지한다. 모든 새 예약에 클래스 연결이 필요하며, 정원은 같은 클래스의 실제 최대 동시 참여 인원을 계산한다.

시작 시간 규칙·휴무일·예약 기간·취소 정책은 조직 공통으로 유지한다. 기존 예약 1,112건의 시간·출결·취소 조건은 보존했다. 구현과 전환·검증 방법은 [클래스별 예약 정책](docs/class-booking-policy.md)을 참고한다.

## Phase 6 일반 수업 화면 공통화

소규모 클래스·과외에서도 자연스럽게 사용할 수 있도록 기존 기능과 데이터를 유지하며 화면을 정리했다.

- 학원 문의 표현을 수업 운영자·담당 강사 표현으로 정리했다.
- 재원·졸업·재원 복귀 표시는 수강 중·수강 종료·수강 재개로 변경했다.
  내부 `NORMAL`·`GRADUATE`·`DELETED` 코드와 예약 제한·예정 예약 취소·복구 정책은 유지한다.
- 보호자 정보는 선택 입력 영역으로 접고, 기존 값이 있으면 펼쳐서 보여준다. 접힌 상태에서도 기존 값은 저장 폼에 포함된다.
- 온라인 수업은 접속 안내를 표시하고 주소·지도 링크를 숨긴다. 오프라인 지도는 유지한다.
- 학습 기록 히트맵은 출석 확인된 종료 수업의 하루 참여 횟수로 색상을 표시하고 실제 시간을 분 단위로 안내한다.
- 당시 클래스 소개와 조직 예약 규칙의 차이를 안내했다. 후속 클래스별 예약 정책에서는 시간·정원을 실제 클래스 규칙으로 전환했다.

기본 1년 수강 기간·반복 등록 방식·클래스별 정책은 이번 단계에서 변경하지 않았다.
자세한 범위와 검증·배포 기록은 [공통화 계획 Phase 6](docs/service-generalization-plan.md#phase-6)을 참고한다.

```bash
npm run typecheck
npm run test:unit
npm run test:db
npm run build
npm run test:generalization:ssr
```

## 5. 상담 신청 정책 (비회원)

### 목적

- 회원가입 전 이탈 최소화
- 오프라인 상담 중심 업종에 적합한 진입 구조 제공

---

### 상담 신청 플로우

```
클래스 상세 페이지
 → 상담 신청하기
 → 이름 / 연락처 입력
 → 상담 신청 완료
```

### 상담 신청 폼 항목

- 이름
- 연락처 (전화번호 또는 메신저)
- 문의 내용 (선택)

---

### 시스템 처리 정책

- 상담 신청 시 User 계정은 생성하지 않음
- 별도의 상담 엔티티로 관리

```text
type: guest
status: pending (상담 대기)
```

---

### 사용자 안내 메시지

> 상담 신청이 완료되었습니다 🙌  
> 담당자가 연락드려 수업 안내를 도와드릴게요.

## 9. 프로그램(수업 클래스) 관리

### 개요

하나의 조직(Organization) 내에서 여러 프로그램(수업)을 운영할 수 있다.
예: 미술학원에서 "유화반", "수채화반", "드로잉반" 등 별도 운영

### 관리자

**클래스 관리 (CRUD)**

- 클래스 생성: 제목, 상태(초안/활성/보관), 부제목, 설명, 강사, 난이도, 가격
- 커버 이미지 (파일 업로드)
- 클래스 수정/삭제
- 클래스 삭제 시 해당 클래스에 스케줄이 있으면 삭제 불가

**클래스 상태**

- `DRAFT`: 초안 (비공개)
- `ACTIVE`: 활성 (수강생이 선택 가능)
- `ARCHIVED`: 보관 (비공개)

**스케줄 생성 시**

- 클래스가 2개 이상: 클래스 선택 UI 표시
- 클래스가 1개: 자동 선택 (UI 생략)

### 일반 사용자 (Student)

**스케줄 등록 시**

- 클래스가 2개 이상: 날짜 선택 후 클래스 선택 다이얼로그 표시
- 클래스가 1개: 기존 플로우 유지 (시간 선택만)

**중복 예약 방지**

- 모든 클래스를 통틀어 같은 시간대에 중복 스케줄 생성 불가
- 예: "유화반" 10:00~13:00 등록 시, "수채화반"에 같은 시간 등록 불가

## 10. 스케줄 및 예약 관리

관리자 → 설정 → 일정 설정의 **수강생 신청 차단 요일**에서 매주 휴무일을
선택할 수 있다. 한국 시간의 수업 시작 요일을 기준으로 수강생의 신규 예약을
차단하며, 기존 예약과 관리자의 직접 일정 등록은 유지한다. 기본값은 모든 요일
허용이다. 전체 요일 차단과 차단 해제도 가능하며, 변경 후 **설정 저장**을 누른다.

배포 시 `0028_student_booking_weekdays.sql` 마이그레이션을 먼저 적용해야 한다.

예약 규칙 공통화 Phase 3은 분 단위 수업 길이·시작 범위·간격·접수 마감과 최대 동시 인원 계산을 지원한다.
실제 반영은 `0032_booking_policy.sql` → `0033_booking_policy_fresh_snapshot.sql` → 새 앱 순서이며 구현·검증 상태는 [공통화 계획](docs/service-generalization-plan.md#phase-3)을 따른다.
예약 기간 공통화 Phase 4는 **월별 오픈** 또는 **오늘 기준 N일** 중 하나를 조직별로 선택한다.
`0034_booking_window.sql` → 새 앱 순서로 적용하며, 자세한 설정·예시는 [예약 오픈 방식](docs/student-booking-window.md)을 따른다.

휴무일 표시는 예약 화면에 반영되고, 예약 RPC 및 직접 INSERT에도 DB 검증이
적용된다. 로컬 검증: `npm run test:unit`, `npm run test:db`.

### 일반 사용자 (Student)

- 본인이 수강 중인 클래스 스케줄 확인
- 예약 / 취소 / 변경 (허용 범위 내)

### 관리자

- 클래스별 스케줄 생성 및 수정
- 수강생별 예약 현황 관리
- 수강생 관리

## 11. 권한 및 역할 정책

### 클래스(Organization) 내 역할

| Role    | 대상        | 권한                                   |
| ------- | ----------- | -------------------------------------- |
| owner   | 슈퍼관리자  | admin 관리, 모든 기능 관리             |
| admin   | 관리자      | 클래스 관리, 상담, 수강생, 스케줄 관리 |
| student | 일반 사용자 | 예약 및 스케줄 확인                    |

- 역할은 클래스 단위로만 적용
- 한 사용자는 여러 클래스에서 모두 `student`일 수 있음

## 14. 설계 핵심 원칙

1. 관리자가 핵심 고객이다
2. 일반 사용자의 role은 항상 `student`이다
3. 회원가입은 항상 클래스 컨텍스트 기반이다
4. 상담 → 결정 → 초대 → 가입 흐름을 따른다
5. 클래스 상세 페이지는 홍보용 랜딩이다
6. 예약·상담·관리 경험이 서비스의 핵심 가치다

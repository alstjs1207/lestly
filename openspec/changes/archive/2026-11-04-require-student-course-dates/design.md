# Design

## Context

현재 0030의 save_managed_student는 신규 시작일과 종료일을 자동 생성하며 0039의 guard_schedule_write는 null 경계를 검사하지 않는다. 앱 생성 API와 저장 helper도 1년 종료일을 중복 생성한다. 기존 기간·상태 변경은 조직/학생 advisory lock과 확인 토큰으로 보호된다.

## Goals / Non-Goals

생성·수정·일괄 등록과 예약 경로의 수강 기간 검증을 일치시킨다. 계정 접근 정책, 고객 데이터 backfill, 기존 예약 취소나 운영 DB 적용은 범위 밖이다.

## Decisions

- 종료일은 자동 입력하지 않는다. 신규 시작일만 KST 오늘로 정규화한 뒤 종료일 필수·순서를 검증한다. 기존 둘 다 null인 수정은 허용하여 기본 정보 변경과 기록을 보존한다.
- 날짜 필드와 월말 보정 helper를 공통화하여 단건과 일괄 화면에서 같은 버튼을 사용한다. 시작일이 없으면 버튼을 비활성화하고 시작일 변경은 종료일을 덮어쓰지 않는다. 신규 기본 시작일은 오늘, 종료일은 빈 값이다.
- 0040 migration에서 기존 저장 RPC의 권한·확인 토큰·fast path 로직을 보존하고 신규 기본값과 조건만 변경한다. 프로필 트리거의 날짜 쌍 검사는 날짜를 실제 변경할 때만 적용하여 legacy 불완전 데이터의 무관한 기본 정보 수정은 허용한다.
- 예약은 기존 guard의 조직/학생 잠금을 유지한 뒤 기간을 검사한다. 기존 guard 본문에 누락 검사만 추가한다. guard의 실행 열(학생·클래스·시간 등)은 유지하므로 조회·취소·출결만 변경하는 경로에는 새 기간 검사가 실행되지 않는다. 가용 시간 RPC도 미등록 이유를 반환한다.
- DB 회귀는 기존 0039까지의 동작 검사 뒤 0040을 적용해 이전 예약·이력·접근 정보 보존과 새 저장/예약 경계를 실제 SQL로 검증한다.

## Risks / Trade-offs

- 기존 시작일만 있는 데이터 → 기본 정보만 수정하는 DB fast path는 보존하되 폼에서 다음 저장 시 종료일 보완을 요구한다. 새 예약은 제한한다.
- 일괄 화면은 현재 날짜가 없다 → 명단 공통 기간을 제공하고 제출 전에 검증한다. 일부 등록 성공 후 재시도 시 성공 행은 그대로 유지한다.
- 브라우저 시간대/월말 → KST 오늘 계산과 달력 월 연산을 공통 helper로 처리하고 윤년·말일·연도 경계를 검증한다.

## Migration Plan

새 migration을 먼저 적용하고 새 앱을 배포한다. 이번 작업에서는 SQL 파일과 로컬 검증만 준비한다. 기존 프로필/예약을 갱신하지 않으므로 rollback은 이전 함수 정의 복원과 앱 rollback이며 고객 데이터 복구는 필요하지 않다. 실제 DB 적용 전후 기존 행 비교는 별도 배포 작업에서 수행한다.
